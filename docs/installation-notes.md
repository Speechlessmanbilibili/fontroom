# 描述文件实现与安装实测

## 格式与字体身份

Apple 的 `com.apple.font` 接受独立 TrueType（`.ttf`）或 OpenType（`.otf`）文件，每个字体子载荷包含一个文件。字体集合 `.ttc`、`.otc` 先拆分为独立文件，再交给生成器。

设备使用字体内部的 PostScript 名称识别字体。相同 PostScript 名称对应同一字体身份，维护字体版本时应核对该名称。

`Name` 是安装前的用户可见名称；Apple 说明安装后会使用实际字体名称替换。项目沿用文件名作为安装前的标签，字体家族与样式来自字体内部名称。

参考：[Apple Font 描述文件定义](https://developer.apple.com/documentation/devicemanagement/font)。

## 原始字体字节与 plist

生成器将字体原始字节传给 `Font`：

```python
"Font": path.read_bytes()
```

`plistlib` 在 XML 格式中自行进行 Base64 编码；当前项目使用二进制 plist，直接保存字节。提前将字体字节转换为 Base64 文本会造成重复编码，安装器得到的内容会偏离原字体。

既有排障曾通过比较可用描述文件与自生成文件的 `Font` 值，定位重复编码：前者保留字体文件魔数，后者的内容是 Base64 文本。修正原始字节写入后，原先失败的安装文件恢复正常。

结构对照参考过 [Keyman 的公开字体描述文件](https://github.com/keymanapp/r.keymanweb.com)。

## HTTP 分发

描述文件响应使用单一的 `Content-Type: application/x-apple-aspen-config`，发送原始文件流。既有 Safari 排障中，gzip 压缩数据被直接交给安装器解析，随后出现“包含无效字体”；服务器因此使用原始文件流。

服务以较大的发送缓冲区和分块复制分发文件，支持 `Range` 字节范围请求，客户端断开时结束对应传输。预生成文件采用临时文件与原子替换的方式提交，防止客户端下载到正在写入的文件。

## 排查步骤

出现“包含无效字体”时，依次核对：

1. 读取 plist，确认顶层类型为 `Configuration`，字体子载荷为 `com.apple.font`。
2. 将每个 `Font` 字节值与对应字体原文件逐一比较，并检查字体文件本身。
3. 核对字体内部 PostScript 名称与家族、样式信息。
4. 检查 HTTP 下载字节、文件长度和描述文件 MIME 类型。
5. 区分下载、待安装项解析和最终安装三个阶段，记录具体失败位置。

需要隔离问题时，可用已有可用描述文件逐项对照：替换字体数据、重新序列化、单独调整标识或名称，并递归比较各字段。
